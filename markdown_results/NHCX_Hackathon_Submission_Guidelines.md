# 5. Detailed Submission Package Requirements


**A. README.txt/.docx/.pdf Requirements**


The README must clearly include:


●​ Brief Functional Scope
●​ High-Level Architecture
●​ Tools and Libraries Used
○​ Clearly categorized as:
■​ Open Source
■​ Closed Source
●​ Setup Instructions
●​ Dependencies
●​ Implementation Details


The README should enable evaluators to understand and execute the solution easily.


**B. Video Demonstration Requirements**


The video must:


●​ Be a complete end-to-end demonstration
●​ Clearly showcase:
○​ Key features
○​ Functional workflow
○​ Implementation highlights
●​ Optional:


○​ Voice-over explanation
○​ On-screen annotations


The video must clearly demonstrate that the solution is functional and working.


**C. Source Code Requirements**


Participants must include:


●​ A ZIP file of the complete source code, following correct naming conventions
●​ All scripts, modules, configuration files, and dependencies required to run the solution
●​ Directory structure that is clean, readable, and logically organized


The code must correspond exactly to the version demonstrated in the video and described in the
**README.md** (as per the code freeze protocol).


**D. FHIR Bundle and FHIR Mapping Document Requirements**


Participants must include:


●​ Properly structured FHIR Bundle TXT files
●​ Corresponding FHIR Mapping Excel document
●​ All files placed inside the output folder using the prescribed naming conventions


These outputs must fully match the test input cases defined in the problem statement.

**Hackathon Authority & Governance Clauses**


**1. Judging Authority**


1.1 The evaluation of all submissions shall be conducted by the duly appointed Jury Panel and/or
Organizing Committee.

1.2 The decision of the Organizing Committee and Jury Panel shall be final, binding, and
non-contestable in all matters relating to evaluation, scoring, shortlisting, disqualification, and
declaration of winners.

1.3 No correspondence, appeal, re-evaluation request, or dispute regarding scores, ranking, or
results shall be entertained.


**2. Evaluation Criteria & Discretion**


2.1 Submissions shall be assessed based on predefined evaluation criteria, which may include but
are not limited to:


●​ Problem understanding
●​ Technical implementation
●​ Innovation and creativity
●​ Code quality and architecture
●​ Scalability and feasibility
●​ Documentation and presentation


2.2 The Organizers reserve the right to modify, refine, or apply additional evaluation parameters
at their discretion to align with the objectives of the Hackathon.


2.3 The Organizers may apply both qualitative and quantitative assessment methods as deemed
appropriate.


**3. Technical Execution & Deployment Disclaimer**


3.1 The Organizers are not obligated to execute, deploy, debug, or modify any submitted code.


3.2 Submissions that:


●​ Lack clear execution instructions,
●​ Do not include required dependency files,
●​ Fail to run within reasonable effort and time, or
●​ Are incomplete or improperly packaged


may be disqualified or scored accordingly at the sole discretion of the Organizers.


3.3 It is the sole responsibility of participants to ensure that their submissions are functional,
complete, and reproducible.


**4. Disqualification**


4.1 The Organizers reserve the right to disqualify any participant or team in case of:


●​ Plagiarism or copied content
●​ Misrepresentation of authorship
●​ Use of unauthorized tools or unfair means
●​ Violation of Hackathon rules or code of conduct


4.2 The decision to disqualify shall be final and binding.


**5. Tie-Breaker**


5.1 In the event of a tie in scoring, the Jury Panel reserves the right to determine the winner based
on additional evaluation parameters or deliberation.


5.2 The tie-breaker decision shall be final and not subject to review.
